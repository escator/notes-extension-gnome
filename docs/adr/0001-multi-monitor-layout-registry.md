# ADR-0001: Реестр раскладок для нескольких мониторов

- Статус: accepted (пользователь, 2026-10-20)
- Дата: 2026-10-20
- Задача: [tasks/001-multi-monitor-layouts](../tasks/001-multi-monitor-layouts/README.md)

## Контекст

Расширение работает с N мониторами, но позиции заметок хранятся в `N_state` в координатах, относительных primary-монитора, без привязки к конфигурации мониторов. При отключении второго монитора заметки оказываются вне видимой области; единственный механизм возврата — ручная кнопка со случайным размещением. Нужны: сохранение раскладки на каждую конфигурацию мониторов, автоматическое восстановление, авто-сбор заметок в видимую зону при исчезновении мониторов. Анализ: [01-analysis.md](../tasks/001-multi-monitor-layouts/01-analysis.md).

## Решение

1. **Глобальные координаты.** Позиции хранятся и применяются в координатах сцены (мониторы = единое полотно). Абстракция «относительно primary» удаляется.
2. **Сигнатура конфигурации по геометрии.** Ключ раскладки — каноническая строка из логических геометрий мониторов (`WxH+X+Y`, сортировка, `,`). Без EDID/имён — работает на любом железе, X11 и Wayland.
3. **Единый реестр `layouts.json`.** Один JSON в DATA_PATH: стабильные id заметок (`seq`), атрибуты (цвет, шрифт), слепки раскладок `{сигнатура: позиции}` с `savedAt` (epoch-мс) и вытеснением LRU, лимит 8 схем. Запись атомарная (`GLib.file_set_contents`) + `.bak`. Текст заметок остаётся в `N_text` (пишется часто, не раздувает реестр).
4. **Fold вместо рандома.** При смене конфигурации: есть схема — применить (с клампингом как страховкой); нет — детерминированный каскад в primary для заметок вне объединения мониторов; результат сохраняется как новая схема.

Концепция: [02-architecture.md](../tasks/001-multi-monitor-layouts/02-architecture.md).

## Альтернативы (отклонены)

- Добавить номер монитора в `N_state` — привязка к порядку перечисления и железу; не решает хранение нескольких раскладок.
- Хранить раскладки в gsettings — не для массивов данных такого объёма.
- Текст заметок в общий JSON — реестр переписывался бы целиком на каждое сохранение текста.
- SQLite / внешняя БД — зависимость, избыточно для десятков КБ данных.

## Последствия

- Положительные: точное восстановление раскладок по конфигурациям; заметки никогда не остаются за экраном; предсказуемый fold; одна точка записи позиций; чистая тестируемая логика (`layouts.js` без shell-зависимостей).
- Отрицательные / риски: разовая миграция `N_state` → реестр; изменение строки в `prefs.ui` требует обновления переводов; один файл реестра — mitigated атомарной записью и `.bak`.

# 01. Анализ: нативная клавиатурная обработка текста в GS 42

Факты установлены чтением исходников GS 42.9 и живым тестом сценария 4
задачи 002 (лог `tmplog/test_4.log` — ошибок расширения нет).

## Как на самом деле устроены клавиши текста в GS 42.9

- `clutter-text.c`: **clipboard-биндингов у ClutterText нет вовсе** — в
  binding pool установлен только `select-all` (Ctrl+A). `key_press` при
  `!editable` сразу возвращает `PROPAGATE`, не обработав ничего.
- `st-entry.c` (`st_entry_key_press_event`): класс-обработчик **St.Entry** —
  именно он обслуживает клавиши, когда внутренний ClutterText их не взял:
  - **paste**: Ctrl+v / Ctrl+V / Shift+Insert → `st_clipboard_get_text(CLIPBOARD)`
    → колбэк делает `delete_selection` + `insert_text(cursor)` → `return TRUE`.
    **Проверки editable нет.**
  - **cut**: Ctrl+x / Ctrl+X → копирует выделение в буфер +
    `delete_selection`. Проверки editable нет.
  - **copy**: Ctrl+c / Ctrl+C → копирует выделение (для парольных полей —
    запрет по password_char).
- `clutter_text_delete_selection` / `insert_text` — буферные API без гейта
  `editable`: работают и на не-редактируемом тексте.
- Фокус: `clutter_text_button_press` берёт key focus при `editable ||
  selectable` — клик по read-only заметке даёт фокус её тексту.

## Баги, найденные при выполнении задачи 002 (сценарий 4)

1. **Ctrl+V вставлял в read-only заметку.** Событие: ClutterText (не
   editable) → PROPAGATE → наш `_onKeyPress` (после Ф2 не глотал Ctrl+V в
   read-only) → класс-обработчик St.Entry → безусловная вставка. До Ф2 путь
   закрывала ветка перенаправления (`return true`). Затычка ed573d5
   (глотание v/V/Paste/x/X + Shift+Insert в read-only) закрыла баг, но
   оставила Ctrl+C/X/A зависимыми от недокументированных веток St.Entry —
   поэтому решение: полный перехват (ADR-0002, п. 4).
2. **Ctrl+X вырезал текст из read-only** (латентный, существовал и до 002:
   старая ветка перенаправления смотрела только v/V/Paste). Прикрыт той же
   затычкой; окончательно закрывается полным перехватом.
3. **Ctrl+Z не срабатывает на русской раскладке** (вестка, не проверена
   живьём): keyval при активной кириллице — не `KEY_z`, а кириллический
   keysym; сравнение по keyval (у нас и у St.Entry) не матчится. Решение —
   union-матчинг: keyval ИЛИ hardware keycode (02, §3).
4. **Клин буфера mutter/X11** (не код расширения, память
   `clipboard-wedge-x11`): после нескольких операций буфер немо перестаёт
   работать (колбэки получают null — и у St.Entry, и у нашего меню),
   лечится свежим копированием. Внешнее ограничение; протокол — пережидать.

## Что доказано живьём (сценарии 1–3 задачи 002)

Методы, которыми меню выполняет действия, работают: копирование/вставка через
`St.Clipboard` + `delete_selection`/`insert_text`, undo/redo через
TextHistory, `boundary()` перед мутациями. Клавиатура в 003 использует ровно
их — новый механизм вставки не вводится.

## Точки интеграции

- `NoteBox._onKeyPress` (noteBox.js) — соединён на `noteEntry` раньше
  класс-обработчика St.Entry: любое `EVENT_STOP` полностью уводит клавишу от
  натива. Точка полного захвата клавиатуры уже существует.
- `NoteTextContextMenu._on*Activated` (menus.js) — реализации действий,
  которые поднимаются в общий слой (02, §1).
